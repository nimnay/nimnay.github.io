NVIDIA × CLEMSON · BENCHMARK · 2026

VANTAGE-Bench

An open benchmark for vision-language models on fixed-camera operational video, built with NVIDIA, used to evaluate their Cosmos 3 models, and actively expanding into 3D spatial reasoning.

SITE DATASET CODE LEADERBOARD

PROBLEM

Vision-language models are evaluated almost entirely on curated, web-scraped imagery. Physical AI deployments look nothing like that: a fixed camera, a fixed scene, long stretches of nothing, and the thing you actually care about happening at the edge of the frame. Existing benchmarks weren't built to measure whether a model can reason about that footage the way an operator does.

MY CONTRIBUTION

The work spans the benchmark end to end: extending a fork of VLMEvalKit into the distributed evaluation service that runs every task, and building the pseudo-labeling pipelines, dataloaders, and model inference paths feeding it. The public site, leaderboard, and submission portal are mine to build and maintain, along with the support that comes with them: submission debugging, format questions, and adding models as they land.

Dataset and task expansion runs alongside that: deciding what gets measured next, specifying it, and building the data behind it.

Single-object tracking I owned outright: annotation specification, metric definition, dataset construction, and baselines. Existing tracking benchmarks assume systems that carry explicit state frame to frame, so the task needed reformulating for how VLMs actually run: one instruction, one pass, a full trajectory out, with metrics that separate tracked badly from didn't track at all. Building the data meant recovering object identities from footage annotated with detections only, with models proposing inside constraints and human labels defining ground truth, so a pipeline error could affect what was inferred, never the underlying annotation.

Getting that spec right mattered more than the modeling. Ambiguous instructions produce annotations that disagree with each other, and a benchmark built on disagreement measures nothing.

ARCHITECTURE

Three stages, deliberately decoupled so a change in one doesn't invalidate the others.

STAGE 1 · GROUND TRUTH
Annotation spec → expert labeling → pseudo-labeling pipeline → dataloaders
STAGE 2 · EVALUATION
Forked VLMEvalKit → distributed inference workers → per-task metrics
STAGE 3 · PUBLICATION
Submission portal → validation → public leaderboard

DATASET

35,027 expert annotations · 3,346 media assets · 8 / 4 tasks / pillars

Eight tasks span four reasoning pillars, so a model can't score well by being good at one kind of question. Everything is public on Hugging Face, with 12k+ downloads to date.

EVALUATION & RESULTS

The evaluation service runs frontier and open models against every task under identical conditions and publishes per-pillar breakdowns rather than a single number. Where a model falls off is more useful than its average.

Holding the model fixed and changing only the footage, semantic question answering barely moves while grounding collapses: roughly 30 points on causal event verification, 24 on spatial pointing. The models still understand what they're seeing. They've lost the ability to say precisely where and when.

Scale doesn't close it. Quadrupling parameters within one model family improved high-level reasoning meaningfully and spatial precision almost not at all, which points at architecture and training priors rather than capacity.

NVIDIA used the benchmark to evaluate Cosmos 3 in their technical report.

IMPACT

·Featured in the GTC Taipei keynote.
·Used to evaluate NVIDIA's Cosmos 3 models in their technical report.
·12k+ dataset downloads, with an open leaderboard accepting external submissions.

IN PROGRESS

VANTAGE-Bench is a live benchmark, not a finished artifact. The current expansion adds 3D reasoning, moving beyond image-plane coordinates to grounding in metric space, where a model has to reason about depth and real-world geometry rather than pixel positions. It's the capability that matters most for physical deployment and one the benchmark doesn't yet cover.

New tasks and data are landing continuously, with the leaderboard and evaluation service built to absorb them without re-running what's already scored.

LESSONS

Annotation design is benchmark design. Most of the quality in this project gets decided before any model runs, in how precisely the task is specified and how disagreement between annotators is resolved. The engineering that follows is comparatively mechanical, and that's the right ratio.

OPEN SOURCE · DEVELOPER TOOLING · 2026

promptpact

Behavioral regression testing for LLM prompts. Declare the behaviors a prompt must satisfy, capture a known-good baseline, and get a check-level signal after any prompt or model change, not an aggregate similarity score that flags every harmless reword.

GITHUB

PROBLEM

LLM output is non-deterministic, so a plain text diff on prompt output is useless: it flags constant false positives (every rewording looks like a change) while potentially missing the one dropped behavior that actually mattered. Prompt changes are code changes with no test suite.

promptpact diffs at the level of the behaviors you declared, so a regression report means "the order-number check broke," not "the wording changed."

DESIGN

A case is an input, an optional system prompt, and a list of named checks. baseline runs the case while the prompt is known-good and saves the result as the reference; diff re-runs it and reports which specific checks regressed. Re-running baseline over an existing one refuses to overwrite without --force, so a reference can't be silently lost.

Because output is stochastic, --samples N draws N outputs per case and each check reports a pass rate rather than a single pass/fail. diff then flags a regression when the rate drops by more than --threshold (default 0.20), rather than when one draw happens to differ.

CHECKS

CHECKFIELDFAILS WHEN
contains text output does not include the exact string
not_contains text output includes the exact string
regex pattern output does not match the pattern
max_sentences count output has more sentences than the count
llm_judge criterion a judge model's verdict on the criterion is FAIL

llm_judge sends the target's output to a judge model inside clearly delimited blocks explicitly labeled as data, so the output can't hijack the judge prompt. With --judge-samples > 1 the judge is called repeatedly and a majority vote decides; a tie is reported INCONCLUSIVE, never silently resolved either way.

ARCHITECTURE

CASES
Versioned YAML: input, system prompt, named checks, suite tags
RUNNER
Target provider call (optionally N samples) → per-check evaluation
BASELINE
Reference results on disk, overwrite-protected
DIFF
Re-run → compare check results or pass rates → regression report
PROVIDERS
Anthropic · OpenAI · Ollama, independently selectable for target and judge

Target and judge are independent, overridable slots. Precedence runs per-case field → CLI flag → project config default, and the judge falls back to the target's provider only when nothing more specific is set.

CLI

$ promptpact baseline --case order-number
saved reference · 2 checks
$ promptpact diff --case order-number # cosmetic reword
no regressions
$ promptpact diff --case order-number # instruction removed
[order-number] REGRESSED contains (baseline=True, current=False)

TECHNICAL DECISIONS

·Checks are independent and named, so one flaky behavior can't mask another and a failure is something you can act on.
·Cases are versioned YAML, not code, so a prompt's contract is reviewable in a pull request.
·Sampling and thresholds are first-class, because a single draw is not evidence about a stochastic system.
·Destructive actions stay human-only: baseline --force is deliberately unreachable from the agent-facing interface.

STATUS

Early and under active development. Working today: init, add, baseline, run, diff, all five check types, three providers, and sampling-based robustness for both target and judge. doctor and mcp-serve, which will expose run, diff, and list_cases to coding agents over MCP, are stubs in progress. Python 3.11+.

LESSONS

The hard part wasn't the runner. It was accepting that "the output changed" is not a useful signal. Once failure had a name, the tool stopped being a diff viewer and became a test suite.

WATT AI × MUSC · CLEMSON UNIVERSITY · 2026

Deep Learning–Based Extraction of Structured Data from Scanned Audiograms in the Electronic Health Record

COMPUTER VISION DOCUMENT AI CLINICAL DATA

OVERVIEW

Hearing-health research is limited by how audiograms are stored: scanned, hand-drawn charts sitting in the electronic health record as images rather than structured fields, unreadable to any analysis that expects a database. In collaboration with MUSC, we built a deep learning pipeline that extracts threshold data from audiograms stored across a tertiary academic health network, combining object detection with calibrated interpolation to convert pixel coordinates into real measurements: frequency in Hz, threshold in dB.

Each audiogram yields 20–25 data points across standard frequencies for both ears, output as JSON for direct EHR integration, turning scanned images into queryable databases for automated hearing-loss classification and longitudinal tracking.

METHOD

Six YOLO architectures were benchmarked across two detection tasks and evaluated on mAP@50, mAP@50-95, precision, and recall. YOLO11s was selected for axis detection (best balance of speed and accuracy) and YOLO11l for symbol detection, prioritizing recall to minimize missed symbols. A three-stage pipeline follows: axis detection extracts calibration markers, symbol detection locates hearing thresholds, and interpolation maps pixel positions into value space: nearest-neighbor on the logarithmic frequency axis, linear on the dB axis.

A second track evaluated four vision-language models on speech-score detection across 98 images and six categories, comparing instruct against thinking variants. Preprocessing improvements significantly boosted consistency and reduced hallucinated values.

WATT AI · MEDIA FORENSICS HUB · CLEMSON UNIVERSITY · 2025

Frame Extraction and Labelling of Social Media Posts

MULTIMODAL LLMS EMBEDDINGS CLUSTERING

OVERVIEW

This project investigates how meaning and influence are constructed across social media text and video by modeling what core message audiences are meant to take away. It covers three related tasks: extracting the main idea from short-form videos using transcripts and video-aware LLMs, standardizing noisy or inconsistent person names into coherent entities, and building user-level profiles that summarize what each account communicates over time.

Together these turn raw social media content into structured representations of messages, people, and communities, supporting analysis of online narratives, coordination, and information flows.

METHOD

Multimodal frame extraction. A pipeline analyzes each video under three conditions (visuals only, visuals plus transcript, and visuals plus transcript plus speaker labels) so the contribution of each modality can be measured directly, and information gain is computed from semantic similarity between conditions using sentence embeddings.

Name standardization. BGE-Large embeddings place semantically similar names near each other and are clustered by cosine similarity; Double Metaphone phonetic codes and Levenshtein distance then catch misspellings, abbreviations, and title variations, with small clusters merged where semantic and phonetic similarity agree.

User modeling. gpt-oss-20b summarizes each user's posts, summaries are embedded with bge-large-en-v1.5, and the resulting clusters are compared against human thematic groupings to assess how well the LLM captures what an account is actually doing.
